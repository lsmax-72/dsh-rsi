# 正式配对实验方案（待确认，未启动）

更新：2026-10-03。以下是可审核的运行方案，不代表已有正式实验授权或效果结果。

## 目的

检验前序真实任务自然生成的 Chat Memory 与 Skill，能否让完整 dsh-rsi 在新的仓库任务上解决更多问题，以及为此增加或减少多少 token。整体比较原始 dsh 与完整插件，不拆成 Memory-only / Skill-only。

## 建议题单与规模

采用本地 SWE-bench Verified，固定 Django 3.0 这一子集，排除已经用于接入调试的两题。按 `created_at`、`instance_id` 排序，取前 4 题作为前序，随后 20 题作为后序。选择只用公开任务元数据，没有按成功结果、正确补丁或隐藏测试筛题。

前序：`10554、10880、10914、10999`。完整 ID、后序题单、公开时间与基础提交见 [候选清单](evidence/proposed-task-manifest-20261003.json)。该序列是实验安排，不把 issue 的创建时间当作模型训练截止时间。

两组各运行 4 个前序和 20 个后序，总计 48 次任务执行；每题每组 1 次，后序得到 20 对结果。这个规模适合首轮固定题单比较，区间可能很宽；不能据此声称对所有仓库稳定有效。若需要重复或扩大，应作为预先定义的新阶段，不挑成功题追加重跑。

## 两组流程

| 阶段 | 原始 dsh | 完整 dsh-rsi |
| --- | --- | --- |
| 初始化 | 无插件服务、工具与资产 | 空资产库，默认中文和自动学习 |
| 4 个前序任务 | 相同公开问题和初始代码，无跨会话插件经验 | 顺序执行，代码每题恢复，资产自然累积 |
| 前序结束 | 保存完整日志和成本 | 等待有限后台窗口，关闭、保存带日志来源的经验快照；包括错误资产 |
| 20 个后序任务 | 每题独立会话、干净代码和状态 | 每题独立复制同一前序快照；干净代码与会话，不共享后序新增资产 |
| 判分 | 官方测试 | 同一个官方测试环境与判分器 |

两个条件使用相同官方 dsh、模型、基础工具、公开问题、前台预算与测试环境；代码树与评分镜像的实际 HEAD 时间共同固定，避免 Django 开发版本漂移。插件增加的能力属于处理条件。顺序预先固定：后序偶数题先插件组，奇数题先原始组，降低执行顺序与服务时间的系统偏差。

后序提示不点名插件 Skill、不拼入资产正文、不要求每题加载两类资产。消费覆盖率从实际调用与 messages 核验，未自然加载也是要报告的结果。答案补丁、隐藏测试、评分结果只进入判分侧。

## 建议预算与失败处理

| 参数 | 拟定值 / 规则 |
| --- | --- |
| 模型 | qwen / qwen3.8-27b，官方 pi-ai 适配，thinking off，无 SDK 重试 |
| 官方宿主 | @deepseek-ai/dsh@0.2.0-rc.2 |
| 前台 | 每题最多 40 次模型调用、每次输出最多 8192 token、墙钟最多 20 分钟，两组相同 |
| 后台 | 每次输出最多 4096 token、默认原生调度；前序合计最多 100 次调用，后序每题副本最多 10 次新增调用 |
| 等待窗口 | 每个前序结束最多 3 分钟；最后前序最多额外 3 分钟，保存未完成/失败状态；后序每题最多 3 分钟 |
| 产品设置 | everyNConversations=2、idleSeconds=30、maxIterations=16、timeoutMs=180000、recallMaxChars=6000、language=zh-CN |
| 容器 | 非 root、只读镜像、任务代码与实验卷独立，2 CPU / 3 GiB、256 PIDs，内部网络仅经固定模型网关访问已授权服务 |
| 任务失败 / 截断 | 保留预算截止补丁做官方判分；停止原因单独保存，不能覆盖 resolved |
| 基础设施故障 | 独立记录；只允许经日志确认的服务/网络/原始环境故障进行 1 次同配置重跑，保留原尝试成本及原因 |
| 不能判分 | 不改算任务失败；报告缺失配对和原因，不临时换题或偷偷缩小分母 |

40 次前台额度是待确认建议，来源是先前真实修复在第 25 次调用前被截断；不是本轮预演的预算增加。正式运行前须确认资源投入，并用统一运行器实现跨容器的前序后台总额及后序“新增调用”限额。恢复快照中的历史 usage 不能当作本题新增成本；不能因跨日重置而突破实验总预算。当前入口不自动执行这个正式方案。

## 指标与解释

1. **主要结果**：两组各解决多少 / 20；同一题新增解决多少、新增失败多少，完整配对表及差异区间。
2. **前台开销**：每题 input/output/total token、调用次数、停止原因、墙钟耗时。多次请求重复上下文计入实际 usage。
3. **学习开销**：前序及后序学习、更新、L2/L3 的全部成功与失败调用，分别记账；缺失 usage 为未知并报告覆盖率。
4. **全链路开销**：两组前序执行 + 后序执行 + 后台；报告 token 绝对增量和比例，固定按 20 个后序任务摊销前序学习。另报每解决一题需要多少 token。
5. **机制诊断**：真实生成的各层资产与 Skill 数量、来源、版本、实际加载率及正文到达请求的证据；不替代官方 resolved。

成功率增加且成本增加时，报告每新增成功的 token 代价，不宣称节省。成功率持平但全链路 token 下降，可报告本题单的效率改善。成功率和成本都无收益，则保留负结果；不能事后改变题单、删除错误资产或只展示成功题。
