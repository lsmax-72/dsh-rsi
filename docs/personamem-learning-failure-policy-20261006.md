# PersonaMem 后台失败与前台答题的预先规则

## 本次解决的问题
当前关闭轮最后一位用户在 Skill 更新超时后没有进入答题，原协议因此不能报告完整八用户准确率。修改方向是让下一轮测量有限预算内实际可用的完整插件：后台学习失败是一个单独结果；已有历史和资产仍能被前台使用时，前台答题质量可以测量。它不会使学习失败变成学习成功。

只修改评测运行器、冻结与离线报告，不修改原生提炼、检索、Skill 工具、版本或生产算法。旧轮继续缺失，不恢复旧轮、不回填答案，也不删旧费用。

## 两种冻结策略
- `require-complete`：默认及全部旧冻结使用。原生学习不结束就停止，不给缺失答案记零分。
- `evaluate-closed-bounded-failure`：只允许新方案在首次派发前明确选择。原生 L0 捕获完整、没有活跃调用或待处理队列、实际学习账本全部闭合后，作业为 `failed`/`paused` 且失败码仅为 `ABORTED` 或带实际拦截记录的 `BUDGET_EXHAUSTED` 时，可冻结已有资产进入答题。

`ABORTED` 表示已闭合的操作中断；此规则本身不能证明中断根因或保证都是时限耗尽。未知错误、明确的基础设施错误、还在运行、未完整捕获或关闭产生的 `interrupted` 均停止。仅有待触发画像、没有已记录失败作业的状态也不会被此规则放行。不得通过扩充次数/时间、救援提炼、人工编辑资产或给模型答案来恢复失败。

答题前关闭学习；原题历史、共同时间来源说明及截止点在两组保持。答题后除作业来源和 L0-L3 数量，还对比 Memory 正文及历史版本、Skill 正文/版本/资源、画像文件完整导出内容。答案不得变成学习输入。

## 报告怎么计算
已测到的每题输出仍按原官方提取方法评分，包括正常协议保存的中断输出；完全缺失的答案不补零。完整八用户配对都结束才能出全组估计，按用户做成对 bootstrap。单列 `completedLearners` 和 `closedBoundedFailedLearners`，保留实际前台/后台 token 与未知 usage，失败学习费用计入总成本。

新 receipt 声明实际策略、失败作业及 `learning.json` SHA256；离线报告检查冻结策略、失败来源、实际闭合账本和内容哈希。默认策略不得接受事后改成宽松规则的 receipt。

已接触用户的复验使用 `preexposed-development-replication`、`FROZEN_PERSONAMEM_REPLICATION`、`independenceClaim:false` 和 `COMPLETE_PREEXPOSED_SAVED_RESULTS`。复验用于开发比较，不充当独立盲测或全数据集结论。

## v2：独立画像失败的原生证据闭合
新策略 `evaluate-closed-native-failure-v2` 仅供首次派发前明确登记的新冻结。旧 `require-complete` 和 `evaluate-closed-bounded-failure` 的逻辑不改；已有失败、缺失答案与费用不重分类、不恢复。v2 不再要求为独立 L2/L3 错误制造一条失败历史作业。

v2 同时核验：公共历史对应的 L0 数量完整、学习已关闭、没有活跃请求或待处理队列；全部实际后台派发闭合；每个原生后台调用保存终态，最新画像状态与持久运行记录一致。使用原生 Session 重放每次派发的日志前缀，消息必须逐项一致。仅接受原生日志支持的 `ABORTED` 或 `BUDGET_EXHAUSTED`；仍运行、未知/基础设施错误、缺日志、未完整捕获、只有待触发而没有真实失败均拒绝。

额度拒绝区分两处：`HOST_LEARNING_QUOTA` 必须与原生结束错误、最后开始的步骤及未派发请求 ID 对应；`HOST_LEARNING_QUOTA_PRECHECK` 仅用于真实历史作业开始前的拒绝，保留作业 ID、范围、日期与额度，不能冒充模型请求。额度证据、当日预约数量、实际后台请求数和本次固定上限必须吻合；预约不能充当上游使用量。这些强条件目前要求一个用户学习过程的账本在同一 UTC 额度日内闭合；未来冻结须避免跨日学习窗口，不能遇到跨日误差后修改旧证据或扩大额度。

失败结果保持 `FAILED_CLOSED_BOUNDED`、`complete:false`，分别列出 `failedJobs` 与 `failedProfiles`。学习失败不充当前台错答或成功；前台使用已冻结资产，完整导出内容/版本/资源前后必须不变。离线报告校验原始日志文件 SHA、公共输入字节、固定预算，并调用同一个 JS 门控重新重放决定，不只相信 receipt 字段。未知费用继续保留。

### 验证及实际边界
- [原生宿主门控](evidence/personamem-native-profile-gate-20261006.json)：17 项控制涵盖工具后拒绝、首请求零派发、已关闭调用、原始终态与输入重建；篡改输入、账本、预算或制造失败作业均拒绝。另通过真实 `process` 触发空合成队列的额度前置拒绝，零新增派发；不是手写失败状态。重启仍保留失败，夹具明确开启学习后原生恢复成功。它不验证真实历史质量。
- [离线报告](evidence/personamem-native-profile-report-20261006.json)：9 项控制核验 profile-only 失败可进入新协议报告，旧策略错配、缺/改日志、改输入/公共历史/额度、预约误计及伪造失败归因均拒绝。包含 45 已知模拟 token 与 1 未知模拟 usage，失败费用未遗漏。这不是实际消费或八用户成绩。
- [Docker 完整链路](evidence/personamem-native-profile-runtime-20261006.json)：原生捕获 2 条用户/助手记录，历史作业完成，保存 1 条 Memory 和 1 个 Skill；独立 L2 首请求因额度被拒绝，原始终态与请求 ID 核验通过。3 次后台及 2 次前台模型夹具请求全部可重建，2 个问题完成，资产正文/版本/资源不变，学习仍失败。模拟用量 100；真实模型调用 0。未证明 Skill 正文加载、资产质量或效果优势；只运行 RSI 夹具，不能据此声称两组真实历史已对齐。
- 原来的 14 门控及 15 报告/已有报告修订保护控制重新通过，0 真实模型调用。
