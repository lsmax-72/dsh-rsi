# 同一任务补跑与资产消费验收

日期：2026-10-03。**真实补丁通过官方判分；Chat Memory 与 Skill 正文均进入后续真实请求，三个指定门槛通过。正式配对实验未启动。** 最初两次失败的记录继续保留，见 [首轮报告](real-pilot-20261003.md)。本次补跑不是新题，不与正式效果样本混合。

## 真实任务与官方判分

继续使用官方 dsh `0.2.0-rc.2`、完整插件与 `qwen3.8-27b`，补跑 `django__django-11292`。任务容器先生成并设置 en_US.UTF-8；要求公开测试使用 `--parallel 1`，没有向 Agent 提供隐藏测试或正确补丁。容器采用非 root、只读 rootfs、capabilities 全部移除、内部网络、实验专用卷和 tmpfs，没有个人目录或资产挂载。

模型产生 6682 字节补丁，官方 SWE-bench `3.0.0` 的 run_instance 给出 `resolved=true`：1 项 FAIL_TO_PASS 与 31 项 PASS_TO_PASS 均通过。评分侧 50 个源码文件与安装包记录一致；评分容器与模型任务分离，评分结果没有回灌学习。

前台实际发送 24 次请求，下一次被试跑总前台上限拦截，真实 turn/end 为 error。必须同时报告“补丁通过官方判分”和“Agent 因预算结束”，不能把正常完成协议说成已通过，也不能将审计驱动报错覆盖为补丁失败。正式协议将继续区分轮次结束、预算状态与官方 resolved。

## 初次学习失败与最小修正

初次后台请求 4 次：原生 L1 合法返回空记忆；Skill 提炼在 4096 输出上限处截断，未写入 Skill。原消费者因共享前台上限耗尽而没有实际请求。随后审计驱动错误地要求每次请求有一个 request/header，产生误报。原始失败日志和空资产状态保留。

已定位两个问题：

- 原生 L1 默认只处理最后 10 条合格消息，dsh 工具密集轮次会产生很多 assistant 消息，开头的用户要求落到窗口之外。宿主适配通过既有 maxMessagesPerExtraction 参数保留同轮完整输入，冻结算法、过滤规则和存储源码没有改动。17 条消息的回归夹具验证用户来源进入“新消息”区并正确存储，真实模型请求为 0。
- 官方 request/header 只记录调用配置变更。审计改为在每条 assistant/message 或 assistant/attempt 之前重建日志前缀；原始 28 次实际请求全部与官方 deriveMessages 一致，没有重新调用模型。

原试跑要求关闭 thinking 的配置未实际生效。现经官方 pi-ai 的 qwen-chat-template、reasoningEfforts 与 reasoning=off 配置关闭；另设 supportsDeveloperRole=false，避免服务拒绝 developer 角色。新请求网关字段 enable_thinking=false，新增会话 reasoning 块为 0；未在网关改写角色或拼接输入。

## 原生资产与实际消费

重提炼仅使用原真实任务的持久日志，未重跑修复、未读取评分结果、未手工写入资产。原生 L1 生成 6 条记忆，原生 Skill 工具创建 1 个中文技能 `rsi-django-repo-fix`，版本为 1。此前失败的空资产库单独保留。

首次独立消费者已实际收到 6 条记忆正文，并通过官方 skill 工具加载完整技能。严格来源检查发现原生召回只返回 content/type/score，不携带 ID，因此原始回执 memoryDelivered=false。宿主适配现只为“同范围内正文与类型唯一匹配”的记录附加 ID 和版本，重复匹配时不猜测身份；提炼、检索、资产正文和冻结源码没有改动。

随后冻结相同资产快照、关闭学习，在新的 `pilot2-delivery-final` 会话做最终验收：

| 门槛 | 实际证据 |
| --- | --- |
| 真实修复 | qwen 补丁官方 resolved=true，1 项目标测试与 31 项回归测试通过 |
| Chat Memory | 6 条正文均进入消费者请求 1、2；source.kind=dsh-rsi、form=memory，refs 的工作区范围、资产 ID、版本与正文相符；来源消息 ID 均存在于真实源日志 |
| Skill | 官方 skill 工具实际加载 rsi-django-repo-fix；非错误工具结果的完整正文进入请求 2，调用 ID、版本 1 与正文 SHA256 相符 |
| 可重建性 | 全部 37 次保留的实际请求通过官方 Session.deriveMessages 的日志前缀重建比对 |
| 资产冻结 | 最终会话前后的记忆与 Skill 正文及版本相同；没有重新提炼或修复任务 |

两次消费者均正常 completed，工具调用仅为 skill。17 条消息窗口回归与带来源 ID 的完整固定响应闭环检查另存回执；56 个核心源码与 10 个界面文件冻结哈希未改变。

还有以下失败需要单列：首次重提炼退出后，tmpfs 中的状态与新请求日志未能导出，仅保留进程错误和容器策略，usage **未知**；为其保守预留 1 次转发额度，不按零计算。修复为实验专用持久卷后，以网关上限 0 诊断，1 次适配器 dispatch 被拒绝、0 次提供商调用。下一次重提炼有 1 次真实转发，服务返回 HTTP 400 “Unexpected message role.”；SDK 报告 0 token，这不是成功推理。再经官方角色兼容配置修正，提炼和消费才通过。

因此 672231 是**可核对请求的已知报告用量**，另有首次恢复失败的未知用量。已知转发 38 次，加首次缺失调用保守预留后最多 39 次，未超过原定 55 次上限。最初两次失败的 721412 token 保持单独记录；全部调试已知累计 1393643 token，未知用量另列。

后台已知用量为 138091 token，包含失败学习与重提炼；没有原始 dsh 对照，不能称为自进化净增量或节省。失败和重复消费均属于接入调试，不进入正式配对效果样本。

## 质量边界与停止状态

三个指定门槛通过，只说明真实修复、原生提炼和两类资产交付可行。最终消费者明确要求加载指定技能，尚未证明自动选择质量、跨任务迁移或整体收益；真实 L2/L3 消费也未验收。

Skill 有一处与真实补丁不一致的描述：声称本例保留 stealth 元组，但实际补丁移除了其中的 skip_checks。正文仍包含本题路径、版本和基线提交，不应直接认作适用于所有任务的可靠经验。资产保持原样、问题如实记录，未通过手工纠正掩盖提炼质量问题。

模型日志外发已取得用户明确授权；任务始终在隔离容器，个人目录与资产未挂载。原先丢失证据的失败，以及初次严格来源审计不通过的回执均保留。正式配对 benchmark 按用户要求停止，题单、规模、预算和质量判定规则待下一阶段讨论。
